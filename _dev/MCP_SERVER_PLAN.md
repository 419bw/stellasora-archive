## 二、 设计决策

### 2.1 原语化，不内置语义判断

服务器只提供**确定性原语**（枚举、统计、精确过滤、关键词检索）；语义判断（读哪些、怎么改）完全交给调用方 LLM。

**理由**：

- 调用方是 LLM 驱动的剧情编辑器，查询模式为「给定角色 + 一句草稿台词 → 该角色的规范台词作锚点」；
- 把方法论（口语浓度排序、语体配额、只取本人台词）写进各工具的 description——**description 就是调用方 LLM 唯一会读的 prompt**。这是 MCP 相对「只读 agent + 口头指令」的唯一增值：枚举完整性、取料纯度、格式清洗这些容易丢失的约束被固化成代码，prompt 会忘，代码不会。

### 2.2 不做相似度检索（`find_similar_lines` 已砍）

曾设计 `find_similar_lines(text, speaker, k)`（中文字符二元组 cosine 排序），2026-10-15 讨论后决定**砍掉**：

1. **规模不成立**：最大可模仿角色约 2,050 句，`read_lines` 一两次调用即可捞完；说话人中位数仅 3 句，「全量给你」比「替你筛选」更便宜；
2. **质量是负资产**：字符二元组 cosine 是 lexical 非 semantic，而语气修正的核心维度是语用（拒绝/招呼/安慰/兴奋）。词汇重叠会返回错锚点，LLM 又会锚在给定示例上——喂错锚点比不给更糟；
3. **分工错位**：调用方 LLM 可自行从草稿提取关键词走 `search_text`，语义提取应发生在调用方。

**重加条件**（满足其一再考虑）：单角色语料增长 10~100 倍（如接入配音全文）；调用方是非 LLM 的确定性管线；用量数据表明调用方反复需要「和这句相似的」。

### 2.3 只读与安全

- **零写入工具**。`story_docs/` 是提取管道生成物，服务器只读消费，任何情况下不写入、不重排、不建旁路索引文件；
- 根目录锁死 `story_docs/`：所有路径参数 resolve 后校验前缀，拒绝穿越；
- 不暴露任意 glob / 任意文件读取——避免把 `_beats/`、`_data/` 等管道生成物和「glob 1000 条截断」坑泄漏给调用方。

## 三、 工具面（5 个原语）

| 工具 | 职责 | 参数 | 编辑器场景用法 |
|---|---|---|---|
| `list_families()` | `os.walk` 全量枚举语体目录 + 每类文件数/台词行数 | — | 调用方了解料库结构；从源头堵 glob 截断坑 |
| `list_speakers(min_lines)` | 枚举说话人及句数 | `min_lines`（默认 1） | 编辑器人物下拉框 / 名称校验 |
| `find_character(name)` | 按语体类分组的每文件本人台词数 | `name` | 语气修正前全局盘点：该角色哪些语体有料 |
| `read_lines(path, speaker?, window?, clean?)` | 结构化台词读取 | `speaker` / `window` / `clean` | `speaker` 挖语体；`window` 取场景上下文 |
| `search_text(query, speaker?)` | 关键词子串全库检索 | `query` / `speaker` | 「多娜说过哪几句带『万送屋』的」 |

### 3.1 各工具 description 草案

description 是给调用方 LLM 的方法论载体，必须写清：

**`list_families`**

> 枚举 story_docs 全部语体目录及每类文件数与台词行数。语体类：characters（个人剧情）、_chat（心链聊天）、dispatch（委托结算演出）、discs（唱片剧情）、events（活动剧情）、storysets（故事集）、main（主线）、npc_bonds（NPC 因缘）、prologue（序章）。口语浓度参考：_chat > events/discs/dispatch > characters/main。

**`list_speakers`**

> 枚举语料库全部说话人及台词句数。注意：说话人名称直接取自原文，存在未归一的脏名（如「???」「"店长"」），调用方应自行做名称规范化。

**`find_character`**

> 统计指定角色在每个语体类、每个文件中的本人台词数（仅统计「**角色名**：「」」形式的本人台词，不含他人转述）。返回按语体类分组的文件列表。选读建议：按语体配额而非句数排序——_chat/characters/discs/dispatch 全读；events/storysets 读 top 3~4 个文件。命中数高不代表语体纯（events 中大量过场与他人对话语境）。

**`read_lines`**

> 读取指定章节的结构化台词。speaker 参数只返回该角色台词（挖语体用）；window 参数返回指定行号前后若干行（看场景上下文用）；clean 默认开启，剔除 `<br>`、`<r=BOSS></r>` 等格式标记。kind 字段：dialogue=对白、thought=内心独白、narration=旁白、action=动作行（如〔发送表情〕，emoji 使用习惯本身是语气信号，勿删）。

**`search_text`**

> 在全部台词中做关键词子串检索，返回命中行、文件与行号，可限定说话人。全库 5.6 万句亚秒级返回。建议由调用方先从草稿台词中提取关键词再调用，而非传入整句。

### 3.2 `read_lines` 返回结构

```json
[
  {"line": 42, "speaker": "多娜", "kind": "dialogue",  "text": "放心交给我们万送屋吧！"},
  {"line": 43, "speaker": "多娜", "kind": "action",    "text": "〔发送表情 `emoji_joy_a`〕"},
  {"line": 44, "speaker": "旁白",  "kind": "narration", "text": "她拍了拍胸脯。"}
]
```

## 四、 台词行定义与清洗规则

**什么算一句「本人台词」**（实测钉死，L0 测试断言依据）：

| 行形态 | 判定 |
|---|---|
| `^\*\*角色名\*\*：` 且行内含 `」` | 本人台词（dialogue / thought） |
| `^\*\*角色名\*\*：〔…〕` | 动作行，保留并标 `kind=action` |
| `**他人**：「…角色名说过…」` | 他人转述，**不计入** |
| `**？？？**：「…」` | 身份未揭晓，归属存疑，不计入 |
| `**中文男**` 等 | 本地化残留行，不计入 |

实测差异：`^\*\*多娜\*\*：` 粗匹配 915 行，剔除 7 行动作行后为 **908**——`find_character("多娜")` 的断言值就是 908。7 行动作行全部位于 `_chat/PM13001.md`（〔发送表情/图片〕）。

**清洗规则**：`<br>`（换行）、`<r=BOSS></r>`（"魔王"富文本替换标记）默认剔除。

## 五、 部署形态

stdio 与 HTTP 双形态，同一实现，`--transport` 选择：

| 形态 | 访问控制 | 适用 |
|---|---|---|
| stdio | 本地全量（客户端以子进程拉起，无网络暴露） | Claude Desktop 等本地客户端 |
| HTTP | **必须过 release gate** + bearer token | 跨机调用（编辑器后端） |

**HTTP 形态的防剧透要求**：复用 `scripts/story/release_gate.py` 的 `is_page(family, id)` / `is_group(group, id)`，过滤未过 gate 的章节——远程调用方可见范围与公开站点一致；stdio 本地形态可全量（环境变量开关控制）。

**Token 鉴权**：FastMCP 自带 auth 偏实验性，用环境变量 token + 轻量 header 校验，不为此引入额外依赖。

## 六、 技术实现草图

```
scripts/mcp/story_mcp_server.py    # 单文件，约 250 行
```

- 依赖：FastMCP（单 pip 包，与 `scripts/` 现有 Python 栈一致）；
- 启动时 `os.walk(story_docs)` 建内存索引：
  - `speaker → {family → {path → [行号]}}`（支撑 find_character / read_lines / list_speakers）
  - 台词行文本进内存（支撑 search_text）
  - 全库解析亚秒级；stdio 形态每次客户端重启都重建，是固定税（列为测试项）
- 安全：root 锁死 `story_docs/`，resolve 后校验前缀；
- 只读：不实现任何写入工具。

## 七、 测试方案

分四层，逐层往上；**L0 不过不上 L1**。

### L0 功能测试（分钟级，无 LLM）

照 `tests/story/` 现有 pytest 惯例（参考 `test_release_gate.py`），新增 `tests/mcp/test_story_mcp_server.py`，全部用**已知答案断言**：

| 断言 | 期望 |
|---|---|
| `find_character("多娜")` 总数 | **908**（不是 915） |
| 动作行 | `kind=action` 保留且标注 |
| `read_lines` 清洗 | 输出无 `<br>`、`<r=BOSS></r>` 残留 |
| speaker 过滤 | 只回该角色行；（思考）标 `thought` |
| 路径穿越 | `../../etc/passwd` 之类被拒 |
| 不存在角色 | 返回空列表，不抛异常 |
| HTTP gate | locked 章节远程不可见、stdio 本地可见 |
| 启动耗时 | stdio 建索引耗时基线（防回归） |

照仓库「每个检查组带植入变异测试」惯例：故意把 speaker 过滤写错、关掉清洗，验证测试抓得住。

### L1 工具调用行为（LLM 在环，不评质量）

记录完整调用序列：轮数、有无无用的 `list_families` 热身、重复调用。**这层数据直接决定 description 怎么改**。同时量每个工具返回载荷字符数，建立 token 成本账。

### L2 E2E 质量测试

**(a) 三臂对照**（无对照组则「MCP 有用」无法归因）：

| 臂 | 设置 |
|---|---|
| A | 无参考，LLM 纯凭印象改 |
| B | 908 句全量原文直接进 prompt |
| C | 走 MCP 工具 |

B vs C 是 MCP 的价值证明：同等质量下省多少 token 与轮次。

**(b) 测试集分层**，每层 3~5 段：

- 正例（社区二创佳作）→ 测「不破坏」，改动行比例应 ≈0；
- 故意 OOC 反例（让角色说文言/自称错误等）→ 测「能修对」；
- 3 句料的稀疏角色 → 测语料不足时的降级行为；
- 长多角色场景 → 测角色切换时的调用模式与 token 累积。

**(c) 可量化代理指标**（把「语气像不像」部分变成事实）：

- **口头禅频率贴近度**：统计优化前后文本中角色标志特征密度（多娜：`~` 结尾率、`嘿嘿`/`万送屋`/自称频率），与官方语料基线分布算相对偏差；
- 改动行比例（防 LLM 过度重写）；
- OOC 残留数（fresh-context 裁判 LLM 计数）。

**(d) 人工 blind review**：评估人不知版本出自哪臂，五维打分——语气贴合 / 用词一致 / 情节连贯 / 改动幅度 / 漏改过改；每输入跑 3 次看方差。

### L3 性能账本

三本账分开记：服务器载荷 token（脚本直接量）/ LLM 每轮 usage / 端到端 wall time。

- 测 usage **不用桌面客户端**（拿不到），写最小 harness（Python + OpenAI 兼容端点，读 usage 字段），顺便控制变量（同 model、同 temperature）；
- 关键指标是「同等质量所需 token」与 **tool-call 轮数**——编辑器场景每轮都是用户可见等待，轮数比单轮大小更伤体验；
- 预期：stdio 工具执行毫秒级，瓶颈全在 LLM，「速度」边际信息量低。

## 八、 落地顺序与未决问题

**顺序**：L0 测试与实现同步写（断言即规格）→ stdio 本地跑通 → L1 观察调用序列、迭代 description → L2/L3 验收 → HTTP 形态（gate + token）→ 交付第三方。

**未决问题**：

1. HTTP 部署位置与维护方（第三方机房 or 我方）；
2. 调用方编辑器使用的 LLM 与端点（影响 L2/L3 基线）；
3. 是否需要 `list_families` 之外的发现能力（如按活动名检索）。
